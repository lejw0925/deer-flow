## 1. Project Overview

**DeerFlow 2.0** is an open-source "super agent harness" built on **LangGraph** and **LangChain**. It orchestrates sub-agents, persistent memory, sandboxed execution, and extensible skills to perform long-running, multi-step tasks such as deep research, report generation, slide creation, image generation, and web page building.

It is a **full-stack application**:

| Layer | Technology | Port / Notes |
|-------|-----------|--------------|
| **Frontend** | Next.js 16, React 19, TypeScript 5.8, Tailwind CSS 4, pnpm | `3000` (dev) |
| **Gateway API** | Python 3.12, FastAPI, embedded LangGraph runtime | `8001` |
| **Reverse Proxy** | nginx (unified entry point) | `2026` |
| **Provisioner** | Optional Kubernetes sandbox provisioner | `8002` |

Public access is through **nginx on port 2026**, which routes:

- `/api/langgraph/*` → Gateway's LangGraph-compatible API (rewritten to native `/api/*`)
- other `/api/*` → Gateway REST API
- everything else → Frontend

## 3. Technology Stack

### Backend

- **Python 3.12+** (managed with [`uv`](https://docs.astral.sh/uv/))
- **uv workspace** with one member: `backend/packages/harness`
- **FastAPI** for the Gateway REST API
- **LangGraph / LangChain** for agent orchestration and tool binding
- **Pydantic v2** for models and config validation
- **pytest + pytest-asyncio** for testing
- **ruff** for linting and formatting
- **Blockbuster** for runtime blocking-IO detection in tests

### Frontend

- **Next.js 16** with App Router and Turbopack dev
- **React 19**, **TypeScript 5.8**
- **Tailwind CSS 4** with CSS-variable theming
- **pnpm 10.26.2+**
- **Vitest** for unit tests, **Playwright** for E2E tests
- **ESLint + Prettier** for lint/format
- **@t3-oss/env-nextjs + Zod** for env validation

### Infrastructure / Tooling

- **nginx** (required for unified local endpoint)
- **Docker / Docker Compose** (recommended deployment path)
- **pre-commit** hooks configured in `.pre-commit-config.yaml`

## 4. Key Configuration Files

| File | Purpose |
|------|---------|
| `config.yaml` (project root) | Main app config: models, tools, sandbox, memory, subagents, channels, summarization, title generation, etc. |
| `config.example.yaml` | Authoritative template. `config_version` field tracks schema changes. |
| `extensions_config.json` (project root) | MCP servers and skill enable/disable state. |
| `.env` (project root) | API keys and secrets (gitignored). |
| `backend/langgraph.json` | LangGraph graph entrypoint: `deerflow.agents:make_lead_agent`; also checkpointer and auth paths. |
| `frontend/src/env.js` | Frontend env schema; defines `NEXT_PUBLIC_BACKEND_BASE_URL`, `NEXT_PUBLIC_LANGGRAPH_BASE_URL`, etc. |
| `backend/pyproject.toml` | App dependencies + dev group + pytest config + uv workspace. |
| `backend/packages/harness/pyproject.toml` | `deerflow-harness` package dependencies. |
| `frontend/package.json` | Frontend scripts, dependencies, package manager. |

Config resolution priority for `config.yaml`:

1. Explicit `config_path` argument
2. `DEER_FLOW_CONFIG_PATH` env var
3. `backend/config.yaml`
4. `config.yaml` in project root (**recommended**)

Values starting with `$` are resolved as environment variables (e.g. `api_key: $OPENAI_API_KEY`).

## 5. Build, Run and Test Commands

Always run from the **repository root** unless otherwise noted.

### Bootstrap & Setup

```bash
make check            # Verify Node 22+, pnpm, uv, nginx
make install          # Backend uv sync + frontend pnpm install + pre-commit hooks
make config           # Generate config.yaml from config.example.yaml (aborts if exists!)
make config-upgrade   # Merge new fields from config.example.yaml into existing config.yaml
make setup            # Interactive setup wizard (alternative to manual config)
make doctor           # Check configuration and system requirements
make setup-sandbox    # Pre-pull sandbox Docker image (optional, recommended for AIO sandbox)
```

### Local Development

```bash
make dev              # Start Gateway + Frontend + nginx with hot-reload → http://localhost:2026
make dev-daemon       # Same, background
make start            # Production mode locally (no hot-reload)
make start-daemon     # Production mode, background
make stop             # Stop all local services
make clean            # Stop + remove backend/.deer-flow + logs
```

### Docker Development

```bash
make docker-init      # Pull sandbox image, build dev images
make docker-start     # Start Docker dev stack (provisioner only if config uses K8s sandbox mode)
make docker-stop      # Stop Docker dev stack
make docker-logs      # View dev logs
make docker-logs-frontend
make docker-logs-gateway
```

### Docker Production

```bash
make up               # Build and start production Docker stack → http://localhost:2026
make down             # Stop production stack
```

### Backend-Only Commands (run from `backend/`)

```bash
make dev              # Gateway API with reload on port 8001
make gateway          # Gateway API without reload
make test             # Run full pytest suite
make test-blocking-io # Run strict blocking-IO gate (tests/blocking_io/)
make lint             # ruff check + format check
make format           # ruff auto-fix + format
make detect-blocking-io  # Static scan for blocking IO candidates
```

Run a single test file:

```bash
cd backend && PYTHONPATH=. uv run pytest tests/test_<feature>.py -v
```

### Frontend-Only Commands (run from `frontend/`)

```bash
pnpm dev              # Dev server with Turbopack → http://localhost:3000
pnpm lint             # ESLint
pnpm lint:fix         # ESLint auto-fix
pnpm typecheck        # TypeScript check (`tsc --noEmit`)
pnpm test             # Vitest unit tests
pnpm test:e2e         # Playwright E2E tests (Chromium, mocked backend)
pnpm build            # Production build
pnpm format:write     # Prettier write
```

> **Known gotcha:** `pnpm check` (which runs `eslint . --ext .ts,.tsx && tsc --noEmit`) is currently broken because `next lint` resolves to an invalid directory. Use `pnpm lint && pnpm typecheck` instead.
>
> **Build secret:** `pnpm build` needs `BETTER_AUTH_SECRET` set (or `SKIP_ENV_VALIDATION=1`). Prefer a real secret.

## 6. Architecture & Module Boundaries

### Harness vs. App Split

The backend is strictly split into two layers:

- **Harness** (`backend/packages/harness/deerflow/`, package `deerflow-harness`, import prefix `deerflow.*`):
  - Reusable agent framework.
  - Contains agents, tools, sandbox, models, MCP, skills, config, memory, runtime.
- **App** (`backend/app/`, import prefix `app.*`):
  - Application-specific code.
  - Contains the FastAPI Gateway API and IM channel integrations.

**Rule:** `app` may import `deerflow`, but `deerflow` **must never** import `app`. This is enforced in CI by `tests/test_harness_boundary.py`.

### Gateway + Runtime

The LangGraph agent runtime runs **inside** the Gateway process (not as a separate LangGraph server). The Gateway exposes:

- Native REST routers under `/api/*`
- LangGraph-compatible paths under `/api/langgraph/*` (rewritten by nginx to `/api/*`)

### Lead Agent Middleware Chain

The lead agent (`make_lead_agent`) assembles middlewares in strict order:

1. **ThreadDataMiddleware** — per-thread isolated directories
2. **UploadsMiddleware** — inject uploaded files into conversation
3. **SandboxMiddleware** — acquire sandbox
4. **DanglingToolCallMiddleware** — inject placeholders for interrupted tool calls
5. **LLMErrorHandlingMiddleware** — normalize model failures
6. **GuardrailMiddleware** — optional pre-tool authorization
7. **SandboxAuditMiddleware** — audit sandbox operations
8. **ToolErrorHandlingMiddleware** — convert tool exceptions to error ToolMessages
9. **SummarizationMiddleware** — optional context reduction
10. **TodoListMiddleware** — plan-mode task tracking
11. **TokenUsageMiddleware** — token usage recording
12. **TitleMiddleware** — auto-generate thread titles
13. **MemoryMiddleware** — queue conversations for memory extraction
14. **ViewImageMiddleware** — inject base64 images for vision models
15. **DeferredToolFilterMiddleware** — hide deferred MCP tools until promoted
16. **SubagentLimitMiddleware** — enforce max concurrent subagents
17. **LoopDetectionMiddleware** — detect repeated tool-call loops
18. **ClarificationMiddleware** — intercept `ask_clarification` and interrupt (must be last)

### Sandbox System

- **Interface:** abstract `Sandbox` with `execute_command`, `read_file`, `write_file`, `list_dir`.
- **Providers:**
  - `LocalSandboxProvider` — local filesystem; host `bash` disabled by default (`allow_host_bash: false`).
  - `AioSandboxProvider` — Docker-based isolation (`backend/packages/harness/deerflow/community/aio_sandbox/`).
  - Provisioner/Kubernetes mode — optional `provisioner` service creates K8s pods.
- **Virtual paths** agents see:
  - `/mnt/user-data/workspace`
  - `/mnt/user-data/uploads`
  - `/mnt/user-data/outputs`
  - `/mnt/skills`
  - `/mnt/acp-workspace` (read-only ACP workspace)

### Subagents

- Built-in agents: `general-purpose`, `bash`.
- Max 3 concurrent subagents per turn (`MAX_CONCURRENT_SUBAGENTS = 3`).
- 15-minute timeout.
- Runs in background thread pools with SSE status events.

### Memory System

- Per-user JSON storage under `.deer-flow/users/{user_id}/memory.json`.
- Optional per-agent memory under `users/{user_id}/agents/{agent_name}/memory.json`.
- Debounced LLM-based extraction of facts, preferences, context.
- Top facts/context injected into the system prompt on the next turn.

### Skills System

- Skills live in `skills/public/` and `skills/custom/`.
- Each skill is a directory containing `SKILL.md` with YAML frontmatter.
- Enabled skills are injected into the agent system prompt.
- Skills can be installed via `POST /api/skills/install` from `.skill` ZIP archives.

### IM Channels

Bridges Feishu/Lark, Slack, Telegram, DingTalk, WeChat, WeCom, and Discord to the Gateway LangGraph-compatible API. Channels run inside the Gateway container in Docker Compose.

### Tracing

Supports both **LangSmith** and **Langfuse** simultaneously via env vars. Callbacks are attached at the graph invocation root so a single trace captures the full run.

## 7. Development Conventions

### Configuration

- Keep `config.yaml` in the project root.
- Use `make config-upgrade` to pick up new schema fields; bump `config_version` in `config.example.yaml` when changing the schema.
- Most config fields **hot-reload** on the next request (models, tools, memory, summarization, etc.).
- Some fields are **startup-only**: `database`, `checkpointer`, `run_events`, `stream_bridge`, `sandbox`, `log_level`, `channels`. These require a restart to change. The authoritative list is in `packages/harness/deerflow/config/reload_boundary.py::STARTUP_ONLY_FIELDS`.

### Paths & Isolation

- Use virtual paths (`/mnt/user-data/...`, `/mnt/skills`) in agent-facing code, not host paths.
- Runtime data defaults to `.deer-flow/` under the project root.
- In no-auth mode, `user_id` defaults to `"default"`.
- Per-user isolation is applied to memory, threads, and custom agent definitions.

### Import Rules

```python
# Harness internal
from deerflow.agents import make_lead_agent
from deerflow.models import create_chat_model

# App internal
from app.gateway.app import app

# App → Harness (allowed)
from deerflow.config import get_app_config

# Harness → App (FORBIDDEN — will fail CI)
# from app.gateway.routers.uploads import ...
```

### Async / Blocking IO

- The backend is async-first.
- Any synchronous blocking IO that runs on the asyncio event loop must be offloaded with `asyncio.to_thread`.
- CI enforces a strict blocking-IO runtime gate in `tests/blocking_io/`.
- Use `make detect-blocking-io` from the repo root (or `make detect-blocking-io` from `backend/`) to generate a static inventory.

### Frontend Conventions

- Server Components by default; add `"use client"` only when interactivity is needed.
- Use the `@/*` path alias for `src/*`.
- Use `cn()` from `@/lib/utils` for conditional Tailwind classes.
- Use inline type imports: `import { type Foo }`.
- Prefix unused variables with `_`.
- Do **not** manually edit `components/ui/` or `components/ai-elements/` — these are generated from registries.

### Documentation Update Policy

When you make code changes, update the relevant docs:

- `README.md` for user-facing changes.
- `CLAUDE.md` (root and `backend/`) for architecture/command changes.
- `frontend/AGENTS.md` or `frontend/CLAUDE.md` for frontend changes.
- Backend feature docs under `backend/docs/` when appropriate.

## 8. Code Style

### Python

- **Linter/Formatter:** `ruff` (configured in `backend/ruff.toml`)
- **Line length:** 240
- **Target version:** Python 3.12
- **Quote style:** double quotes
- **Indentation:** 4 spaces
- **Type hints:** required; use Python 3.12+ syntax
- **Import groups:** `ruff` handles sorting; first-party packages are `deerflow` and `app`

Run before committing:

```bash
cd backend && make format   # auto-fix + format
cd backend && make lint     # check
```

### TypeScript / Frontend

- **Linter:** ESLint (`frontend/eslint.config.js`)
- **Formatter:** Prettier
- **Import order:** builtin → external → internal → parent → sibling, alphabetized, newlines between groups
- Run before committing:

```bash
cd frontend && pnpm format:write
cd frontend && pnpm lint
cd frontend && pnpm typecheck
```

- **Full suite:** `cd backend && make test` (equivalent to `PYTHONPATH=. uv run pytest tests/ -v`)
- **Blocking-IO gate:** `cd backend && make test-blocking-io`
- **Harness boundary:** `tests/test_harness_boundary.py` (CI-enforced)

## 10. Security Considerations

DeerFlow can execute system commands, read/write files, and invoke business logic. **It is designed for deployment in a local trusted environment (loopback-only) by default.**

- **Default sandbox:** `LocalSandboxProvider` has host `bash` disabled (`allow_host_bash: false`). Only enable it for fully trusted single-user workflows.
- **Recommended isolation:** Use `AioSandboxProvider` (Docker) or provisioner/Kubernetes mode for actual command execution.
- **CORS/CSRF:** The Gateway is same-origin by default when accessed through nginx. For split-origin or port-forwarded clients, set `GATEWAY_CORS_ORIGINS` to a comma-separated allowlist.
- **Artifacts:** Gateway forces active web content types (`text/html`, `application/xhtml+xml`, `image/svg+xml`) to download as attachments to reduce XSS risk.
- **Internal auth:** `DEER_FLOW_INTERNAL_AUTH_TOKEN` is used for multi-worker / channel-to-Gateway authentication.
- **Guardrails:** Optional pluggable `GuardrailProvider` can authorize/deny tool calls.
- **Network:** If deploying beyond localhost, use IP allowlists, strong pre-authentication, and network isolation.

## 11. Deployment Notes

### Resource Sizing

| Target | Starting point | Recommended |
|--------|---------------|-------------|
| Local eval / `make dev` | 4 vCPU / 8 GB / 20 GB SSD | 8 vCPU / 16 GB |
| Docker dev / `make docker-start` | 4 vCPU / 8 GB / 25 GB SSD | 8 vCPU / 16 GB |
| Long-running server / `make up` | 8 vCPU / 16 GB / 40 GB SSD | 16 vCPU / 32 GB |

### Docker Dev vs. Prod

- **Dev** (`make docker-start`): bind-mounts source code, hot-reload, mounts host `.venv` volume.
- **Prod** (`make up`): builds standalone images, uses `GATEWAY_WORKERS` (default 4).
- The `provisioner` service is started **only** when `config.yaml` uses `deerflow.community.aio_sandbox:AioSandboxProvider` with a `provisioner_url`.

### Useful Environment Variables

| Variable | Purpose |
|----------|---------|
| `DEER_FLOW_PROJECT_ROOT` | Project root for relative runtime paths |
| `DEER_FLOW_HOME` | Runtime data dir (default `.deer-flow` under project root) |
| `DEER_FLOW_CONFIG_PATH` | Path to `config.yaml` |
| `DEER_FLOW_EXTENSIONS_CONFIG_PATH` | Path to `extensions_config.json` |
| `DEER_FLOW_SKILLS_PATH` | Skills dir (default `skills/`) |
| `DEER_FLOW_CHANNELS_LANGGRAPH_URL` | Channel-facing LangGraph URL in Docker |
| `DEER_FLOW_CHANNELS_GATEWAY_URL` | Channel-facing Gateway URL in Docker |

## 12. Pull Request / Contributing Notes

- Follow the PR template in `.github/pull_request_template.md`.
- **AI assistance disclosure is mandatory:** every PR must state which AI tools were used (or `none`), how they were used, and confirm a human has read and takes responsibility for the change.
- Pre-checkin validation:
  - Backend: `cd backend && make lint && make test`
  - Frontend (if changed): `cd frontend && pnpm lint && pnpm typecheck`
  - Frontend build (if env/auth/routing changed): `BETTER_AUTH_SECRET=local-dev-secret pnpm build`
- Commit messages use conventional style (e.g. `feat:`, `fix:`), though this is a convention, not enforced by tooling.
